### 🔴 A. 會實際踩到、建議立即修

#### A1. `PATCH /api/tickets/:id` 改類別 → `NOT NULL constraint failed` 崩潰 500
- **位置**：`src/routes/tickets.ts`（改類別且原地點不相容時 `newLocationLabel = null`）
- **根因**：`tickets.location_label` 有 `NOT NULL`，寫入 null 觸發 SQLite 崩潰
- **改法**：若改類別後地點不相容，回 `400 VALIDATION_ERROR` 要求使用者重選地點，而非寫 null

#### A2. `csrfGuard` 阻擋無 body 的 Mutation 請求（403）
- **位置**：`src/lib/csrf.ts` 檢查 content-type 必是 application/json 或 multipart
- **根因**：無 body 的 POST（share-token、logout）`api()` 不設 Content-Type → 被擋 403
- **改法**：`csrfGuard` 允許無 body（content-type 為空）的請求通過，僅在「有 body 且非 json/multipart」時 403

#### A3. CSV 匯出 from/to 時區偏差 8 小時
- **位置**：`src/routes/exports.ts`（from/to 直接拼 `T00:00:00.000Z`）
- **根因**：規格 from/to 是台灣日期，但 DB 存 UTC；直接拼 Z 造成台灣 00:00–08:00 的單被漏掉
- **改法**：from/to 先換算為台灣時區對應的 UTC 字串（`new Date(from + 'T00:00:00+08:00').toISOString()`）

#### A4. `POST /api/options` 未防護 `comment_desc` 寫入關聯表
- **位置**：`src/lib/validate.ts` 的 `createOptionSchema`＋`src/routes/options.ts`
- **根因**：SPEC/CLAUDE 明定 `comment_desc` 不參與類別關聯，但 zod 只擋 `type==='category'` 帶 category_ids，`comment_desc` 帶 category_ids 仍會寫入 option_categories
- **改法**：zod `superRefine` 對 `category` 與 `comment_desc` 都禁止帶 `category_ids`

### 🟡 B. 防禦性、資料多才有感

#### B5. CSV update_count 全表掃描 `ticket_updates`（忽略篩選）
- **位置**：`src/routes/exports.ts`
- **改法**：改在主 SQL 用子查詢算 `update_count`，省二次全表掃描

#### B6. hash router 未過濾 query string
- **位置**：`public/app.js` router（`hash.slice(1).split('/')`）
- **影響**：`#/ticket/12?ref=share` 會把 param 解析成 `12?ref=share` → 後端 Number 判 NaN → 400
- **改法**：解析 hash 前先 `split('?')[0]`

#### B7. `toTaipeiDisplay` 遇 Invalid Date 丟未捕捉例外
- **位置**：`src/lib/time.ts`
- **改法**：`if (!iso) return ''`、`if (isNaN(d.getTime())) return ''`

#### B8. D1 動態 IN 陣列無分塊（可能超綁定上限）
- **位置**：`src/routes/tickets.ts`、`src/routes/options.ts`
- **影響**：工單歷史回報多時，`IN (?,?,...)` 超過 D1 綁定上限
- **改法**：大批量 IN 分塊（每 50 個一組），或改 JOIN 取照片

### 🔴 F. 非同步競態與資料清空風險

#### F1. P7 關聯 Modal 尚未載入完成時點「儲存」會清空該類別所有關聯
- **位置**：`public/app.js` `pages.admin` 的 `openAssocModal`
- **根因**：建立 Modal 後立即發出兩個非同步請求載入地點/說明選項，但「儲存」按鈕無 `disabled` 也無 loading 遮罩。若在載入完成前點儲存，`querySelectorAll('input:checked')` 為空 → 送 `POST /api/options/:id/assoc` 帶 `{ option_ids: [] }` → **該類別原本所有關聯被全量覆寫清空**（資料破壞）
- **改法**：選項載入完成前將儲存鈕 `disabled`，並在 Modal 內顯示載入指示器；載入完成後才啟用

#### F2. P7 管理頁 Tab 快速切換引發渲染覆蓋（Stale Response Overwrite）
- **位置**：`public/app.js` `pages.admin` 的 `renderVendors`/`renderOptions`
- **根因**：切換 Tab 更新 `currentType` 後非同步呼叫 render，各 `.then((b) => { content.innerHTML = ... })` 直接覆蓋內容，無 `currentType` 比對。若「廠商」回應較慢抵達，會在「地點」載入後覆蓋 → **Tab 顯示「地點」但內容是「廠商」**
- **改法**：`.then()` 回呼內比對 `if (currentType !== thisType) return`（或記錄請求序號，只接受最新）

#### F3. 平行 401 請求引發雷鳴群（Thundering Herd）與連鎖 Session 簽發
- **位置**：`public/app.js` `silentRelogin`
- **根因**：Session 過期時，含多個平行 API 呼叫的頁面（如 P1 同時請求 `/api/tickets` 與 `/api/options/catalog`）會各自收到 401 並各自進入 `silentRelogin`，同時向 `/api/auth/session` 發多次重複 POST、後端對 LINE 驗證伺服器發多次相同 ID Token 驗證，造成網路開銷與 Cookie 覆寫競態
- **改法**：建立全域 `reloginPromise` 單例，平行觸發的 401 共用同一次靜默重登流程

### 🟡 資料庫索引與分頁穩定性

#### F4. 統計查詢缺少複合索引導致全表掃描
- **位置**：`migrations/0001_init.sql`（`idx_updates_ticket`）＋ `src/routes/stats.ts` month_done 查詢
- **根因**：`ticket_updates` 僅有 `idx_updates_ticket(ticket_id, created_at)`；month_done 需同時過濾 `kind`、`status`、`created_at`，無對應索引 → 每次瀏覽統計頁都全表掃描，隨歷史回報增多延遲線性上升
- **改法**：新增 migration 補 `CREATE INDEX idx_updates_stats ON ticket_updates(kind, status, created_at)`（**不可改 0001**，0001 已套 production，須用新 migration file）

#### F5. 案件列表分頁缺少次要排序鍵（Tie-Breaker）導致分頁不穩定
- **位置**：`src/routes/tickets.ts` GET /api/tickets 的 `ORDER BY t.last_activity_at DESC LIMIT ? OFFSET ?`
- **根因**：多筆 `last_activity_at` 相同（seed 或批次匯入）時排序不確定，`LIMIT/OFFSET` 分頁可能跨頁重複或遺漏案件
- **改法**：加唯一鍵次要排序 `ORDER BY t.last_activity_at DESC, t.id DESC`

### 🟡 UI 行為不一致與死碼

#### F6. 建單頁選取「零關聯類別」引發無限重複 Alert 彈窗

#### F7. 案件詳情主照片與時間軸照片的 Lightbox 行為不一致

#### F8. `src/routes/tickets.ts` 殘留未使用的宣告變數（死碼）

### 🔴 G. 邏輯與運算子陷阱

#### G1. `newVendorId ?? ticket.vendor_id` Nullish 陷阱導致 null 清空失效
- **位置**：`src/routes/tickets.ts` PATCH handler 的 UPDATE 綁定 `newVendorId ?? ticket.vendor_id`
- **根因**：`??` 將 `null` 與 `undefined` 一併視為空值回退。**一旦照既有 D-1 開放 `vendor_id` 可設 `null` 清空，傳入 `newVendorId = null` 時會回退寫回原 `ticket.vendor_id`，永遠無法把已指派的廠商重設為空**（正是 D-1 想解的功能）
- **改法**：**D-1 施工時必須同步處理**——不可用 `?? `，改用三態判斷：`newVendorId === undefined ? ticket.vendor_id : newVendorId`（undefined=不變、null=清空、有值=指派）

#### G2. 類別停用導致關聯選項「永久幽靈孤兒化」
- **位置**：`src/routes/options.ts` `/catalog` 端點（讀全部 `option_categories` 不過濾 active）＋ `src/lib/db.ts` `optionAllowedInCategory`
- **根因**：catalog 讀所有關聯列未過濾 `options.active=1 AND type='category'`。停用類別後其關聯列仍保留（CLAUDE 規則），該類別關聯到的地點/說明 `category_ids.length>0` 不會被判通用，但停用類別在下拉又不可選 → **該地點/說明在全系統所有類別下徹底隱形、無法被選取**（與 CLAUDE「停用類別不 DELETE 關聯」規則衝突）
- **改法**：`/catalog` 的關聯查詢 JOIN options 過濾 `o.active = 1 AND o.type = 'category'`（僅保留有效類別關聯）；`optionAllowedInCategory` 同步確認

#### G3. 常用範本附加的 `includes()` 子字串誤判
- **位置**：`public/app.js` 建單 `pages.new` 與留言框 `pages.ticket`（`if (cur.includes(label)) return`）
- **根因**：以子字串比對防重複附加，若說明欄已含「中庭**其他**設施」而範本標籤為「其他」，`cur.includes('其他')` 為 true → 簡短標籤（其他/漏水/門禁）撞名自訂文字時**無法附加**
- **改法**：改以「附加片段為獨立項目」判斷（如比對 `cur` 以「、」切分後的陣列是否已含該 label），而非裸 `includes`

### 🟡 資料契約與審核留痕

#### G4. 列表 API 遺漏停用廠商標註，與詳情 API 不一致
- **位置**：`src/routes/tickets.ts` GET /api/tickets（列表）vs GET /api/tickets/:id（詳情）
- **根因**：詳情端廠商停用時後綴「（已停用）」；列表端只 `LEFT JOIN vendors v` 輸出 `v.name`，未讀 `v.active` → **同一案件列表顯示正常名、點入詳情才顯示「（已停用）」**，資料契約不一致
- **改法**：列表查詢加 `v.active`，同詳情端後綴「（已停用）」

#### G5. 系統變更留痕遺漏廠商名稱追蹤
- **位置**：`src/routes/tickets.ts` PATCH `changes.push('廠商')`
- **根因**：類別/地點留 before→after（`類別 電梯→門禁`），但指派廠商只寫「廠商」，時間軸無從得知由哪家轉派給哪家，喪失派工歷程追溯
- **改法**：`changes.push(\`廠商 ${oldName}→${newName}\`)`（取舊 vendor name 與新 vendor name）

### P3. 體驗與健壯性

#### G6. Reopen 備註為空時殘留格式符號
- **位置**：`src/routes/tickets.ts` POST /:id/reopen 的 `重新開啟（原狀態：${prevStatusLabel}）：${body.note ?? ''}`
- **根因**：備註未填時時間軸記錄帶尾端冒號的空字串「重新開啟（原狀態：已完成）：」，版面殘留未完成標點
- **改法**：`body.note ? \`：${body.note}\` : ''`（無備註時不帶冒號）

#### G7. 公開派工照片端點缺 `Content-Disposition: inline`
- **位置**：`src/routes/share.ts` GET /:token/photos/:photo_id
- **根因**：內部照片端點（photos.ts）有 `Content-Disposition: inline; filename=...`，公開端點僅 Content-Type + Cache-Control → 部分 Android 內建瀏覽器/通訊軟體可能觸發下載對話框而非頁內渲染
- **改法**：share 照片端點補 `Content-Disposition: inline; filename="photo-{id}.jpg"`（副檔名依 content_type 推斷）

#### G8. zod `optionalText` 拒絕 null 欄位（低風險）
- **位置**：`src/lib/validate.ts` `optionalText = z.string().trim().max(max).optional().or(z.literal(''))`
- **根因**：`{ description: null }` 非 `undefined` 非 `string` → 400。僅外部 HTTP 客戶端/自動化工具送標準 REST `null` 才觸發（SPA 前端送 `undefined` 不影響）
- **改法**：`z.string().trim().max(max).optional().nullable()` 或 `z.preprocess` 將 null 轉 undefined；低風險、可彈性取捨
