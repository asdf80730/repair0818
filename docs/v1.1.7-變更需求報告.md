# 社區修繕管理系統 — 變更需求報告（v1.1.7）

> 本報告整理兩個待實作需求。經五輪外部評審修正，採**多對多關聯**設計。
> 供評審確認後再施工。

## 0. 需求摘要

### 需求 1：類別 → 地點／說明 關聯

建立「類別」與「地點／常用說明」的多對多關聯。建單時選定類別後，地點／說明下拉只顯示該類別關聯的項目（＋通用項目）。

**關鍵設計（經五輪評審定案）：**
- 關聯採**多對多 join 表** `option_categories`（非單一欄位）。
- **「無關聯」的選項視為「通用」，所有類別可見**。
- **0003 只建表、不 seed 任何關聯**（全部通用）。示意與測試所需關聯由測試 fixture 自行插入。
- **E2E mock 補關聯資料**（前端假資料，不碰 DB），驗證「地點限縮」；另加 `assoc=0` 旗標驗零關聯行為。

### 需求 2：留言框常用說明（manager/admin）

manager / admin 在案件留言／回報時，留言框提供「常用說明下拉＋附加按鈕」，與建單頁一致。

> 註：v1.1.5 已把留言／回報合一（§5.3 底部同一個框），「留言框加下拉」是**同一個元件內按角色條件渲染**，不是新元件。
> 這是**前端 UX 決策（業主明示）**，非權限控制——`GET /api/options` 本就三角色可讀，留言權限依 SPEC §3.6。

## 1. 資料模型變動

### 1.1 新增 join 表

新增 `option_categories` join 表，`options` 表**不加欄位**：

```sql
CREATE TABLE option_categories (
  option_id   INTEGER NOT NULL REFERENCES options(id),
  category_id INTEGER NOT NULL REFERENCES options(id),
  PRIMARY KEY (option_id, category_id)
);
CREATE INDEX idx_oc_category ON option_categories(category_id);
```

- `options` 表結構完全不變（含 `UNIQUE(type, label)`）。
- 一個 option（location/description）可同時屬於多個類別；無任何 `option_categories` 列 = **通用**。
- **索引註解**：PK 已覆蓋「查某選項屬於哪些類別」（P7 勾選矩陣）；額外只需 `idx_oc_category` 支援「查某類別有哪些選項」（建單）。`include_inactive=1` 只用到 `idx_options_type` 的 `type` 前綴，仍可用，**不需新索引**。
- **刻意不加 `created_at`**（純關聯表，無稽核需求）。
- **`option_categories` 的 INSERT/DELETE 只允許出現在 `POST`／`PATCH /api/options` 兩處**（寫死位置，防 AI 在建單流程「順手自動建立關聯」）。

### 1.2 既有資料遷移

- **`migrations/0002_seed.sql` 一字不改**（已套用到 production）。
- **`migrations/0003_category_assoc.sql` 只建表＋索引，不 seed 任何關聯**（全部通用）。
- 關聯資料由管理公司在 P7 自行設定（D4 精神）。
- **回滾方案**：先移除後端過濾程式碼（否則查詢 500），再 `DROP TABLE option_categories`，即回到 v1.1.6 行為。

| 檔案 | 變更內容 |

| `src/routes/tickets.ts` | 建單驗證 location 屬於 category 或通用；PATCH 僅欄位變動時驗證；詳情回應補 `category_id`＋`location_id` |

### 2.1 `GET /api/options` 三種模式（寫死）

| 模式 | 行為 | 回應附帶 | 權限 |
|---|---|---|---|
| `?type=X` | 僅 active（現況不變） | **不附 `category_ids`**（建單用，省查詢、不外洩設定） | 三角色 |
| `?type=X&category_id=N` | 該類別關聯 ＋ 通用，僅 active | 不附 `category_ids` | 三角色 |
| `?type=X&include_inactive=1` | 含停用，**不接受 `category_id`** | **每個 item 附 `category_ids: number[]`**（P7 預先勾選的唯一資料來源） | **限 manager/admin**（後端強制） |

- **`type` 必填**（現行後端已強制）；P7 分三次請求。
- **既有 bug 一併修**：P7 目前用 `?type=X`（只回 active），停用選項看不到、無法重新啟用。v1.1.7 讓 P7 改用 `include_inactive=1`。
- **權限在 handler 內判**：`include_inactive=1` 且 committee → `403 FORBIDDEN`（同路由雙權限，不能用 `requireAuth({roles})` 群組）。
- **`category_ids` 附帶的 SQL**：一次 `SELECT option_id, category_id FROM option_categories WHERE option_id IN (...)` 在應用層 group，**不要 N+1**。無關聯者為 `[]`。

### 2.2 `listOptionsQuerySchema`（lib-spec §4 新增）

```ts
export const listOptionsQuerySchema = z.object({
  type: z.enum(['category', 'location', 'description']),
  category_id: z.coerce.number().int().positive().optional(),
  include_inactive: z.enum(['0', '1']).optional().transform(v => v === '1'),
}).superRefine((val, ctx) => {
  if (val.category_id !== undefined && val.include_inactive) {
    ctx.addIssue({ code: z.ZodIssueCode.custom, path: ['include_inactive'], message: 'include_inactive 不可與 category_id 併用' })
  }
})
```

- `include_inactive` 用 `z.enum(['0','1']).transform()`（**不可用 `z.coerce.boolean()`**）。
- **順序固定 `.optional()` 在 `.transform()` 之前**（輸出型別才是 `boolean`）。
- **`category_id` 與 `include_inactive` 併用 → `400 VALIDATION_ERROR`**（superRefine，`path` 指向 `include_inactive`），補測試斷言。
- **新 400/403 一律走既有 zValidator hook／`fail()` 輸出**（`{ok:false,error:{code,message}}`），**禁止在路由內手寫 `c.json`**（lib-spec §2 規則）。

### 2.3 `category_ids` 三態語意（寫死）

| 送值 | 行為 |
|---|---|
| **未帶（undefined）** | **不動關聯**（只更新 label/sort_order/active） |
| **`[]`** | **明確清空，該選項回歸通用** |
| **有值** | **全量覆寫**（非增量）→ P7 前端每次送完整勾選清單 |

zod 用 `.optional()`（區分 undefined 與 `[]`），**不可加 `.default([])`**。**`category_ids` 上限 `z.array(z.number().int().positive()).max(20)`，寫入前 `[...new Set(ids)]` 去重**（防 `[3,3,5]` 撞 PK）。

### 2.4 詳情回應補 id

`GET /api/tickets/:id` 回應**同時補 `category_id` 與 `location_id`**。

- 兩欄在 SPEC §2.1 **無 `NOT NULL`** → 回應可能是 `null`。**前端 `category_id` 為 null 時 → 下拉顯示全部通用**，不得空白或報錯。
- **編輯頁規則（收斂）**：
  - **初次載入**：目前選中的地點即使不屬於該類別，**保留在下拉並標註「(不在此類別)」**，不驗證、可存（歷史不鎖死）。
  - **主動切換類別**：地點清空＋提示「地點已重設，請重新選擇」。
- **舊地點的取得**：前端**直接用詳情回應的 `location_id` + `location_label` 自行插入一個 option** 到下拉頂部並標註，**不額外打 API**（該 option 可能不在任何查詢回應裡，尤其已停用時）。
- **送出防呆**：地點為空時「儲存」鈕 **disabled**（`location_id` 必填）。

### 2.5 驗證規則（寫死）

- **建單（POST）**：驗證 `location_id` 屬於 `category_id` **或為通用**，不符 `400 VALIDATION_ERROR`。
- **編輯（PATCH）**：**僅當 `category_id` 或 `location_id` 有變動時**才驗證（避免歷史資料鎖死）。
- **description 後端不驗**：`tickets` 沒有 `description_id`，後端無從驗證、也不該驗證。說明的關聯僅影響前端下拉顯示。
- **格式驗證在 zod，存在性／關聯性驗證在 route 內呼叫 `lib/db.ts`**（禁止把關聯驗證做進 zod，async refine 會炸型別）。

### 2.6 join 表 type 由應用層強制

SQLite CHECK 不能跨表查詢。**應用層強制**（寫進 CLAUDE.md）：`assertValidAssoc(c, optionId, categoryIds)`：
- ①每個 id 的 `type='category'`、②`option_id` 的 `type IN ('location','description')`、③不得自我關聯。
- **不驗 category 是否 active**（停用只影響下拉顯示，重新啟用即恢復）。
- 失敗 → **`400 VALIDATION_ERROR`**（message 區分三種原因，**不得自創 `INVALID_ASSOC`**）。
- **`assertValidAssoc` 必須在任何寫入之前執行**（純讀）——先驗 `category_ids` 全為 `type='category'`、再 upsert、再寫關聯。避免兩階段寫入中途失敗留下半套資料（D1 無互動式交易）。

### 2.7 權限

寫入走 `POST/PATCH /api/options`（manager/admin，D5）→ 沿用，**不另開 `/api/option-categories` 端點**。

### 2.8 「先刪後插」授權＋兩階段寫入

**`POST /api/options`**（upsert）不能與關聯寫入放同一個 `batch()`——`batch()` 無法把前一條結果餵給後一條。**寫死做法**：

```
第 0 趟：assertValidAssoc（純讀，先驗 category_ids 全為 type='category'）  ← 任何寫入之前
第 1 趟：INSERT ... ON CONFLICT(type,label) DO UPDATE SET active=1, sort_order=?
         RETURNING id                          ← D1 支援 RETURNING；upsert 命中既有列時 meta.last_row_id 不可靠
第 2 趟：batch([ DELETE ... WHERE option_id=?, INSERT INTO option_categories ... ])  -- 僅當 category_ids 有值或 []
```

- **此為 CLAUDE.md 規則 2「多步驟一律 batch()」的明文例外**（需先取 id 的兩階段寫入）。PATCH 因 id 來自 URL，可單趟 `batch()`。
- **禁止用 `meta.last_row_id` 當 upsert 後 id**，一律 `RETURNING id`。
- DELETE 的 WHERE **只能是 `option_id = ?`**，絕不可 `WHERE category_id = ?`。
- **`option_categories` 的 DELETE 只允許出現在 `POST`/`PATCH /api/options` 兩處**。

### 2.9 `POST /api/options` upsert 與 `category_ids` 交互

upsert 重啟舊選項時帶 `category_ids`：與 PATCH 同語意，**全量覆寫**；未帶則不動。

### 2.10 過濾 SQL 範本（防重複列）

```sql
SELECT o.id, o.label, o.sort_order
FROM options o
WHERE o.type = ?1 AND o.active = 1
  AND (
    EXISTS (SELECT 1 FROM option_categories oc
            WHERE oc.option_id = o.id AND oc.category_id = ?2)
    OR NOT EXISTS (SELECT 1 FROM option_categories oc2
                   WHERE oc2.option_id = o.id)        -- 通用
  )
ORDER BY o.sort_order, o.id;
```

## 3. 前端變更

| 頁面 | 變更內容 |
|---|---|
| **建單頁（P2）** | 選類別 → 地點／說明顯示「該類別關聯 ＋ 通用」；**未選類別時地點與說明下拉都 disabled ＋ placeholder「請先選擇類別」**（一致處理） |
| **詳情頁留言框（P3）** | manager / admin 加「常用說明下拉＋附加按鈕」（同一元件內按角色條件渲染）；從案件 `category_id` 過濾（null → 顯示通用） |
| **管理頁（P7）** | 改用 `include_inactive=1`（修停用顯示 bug）；每列「所屬類別」勾選矩陣（原生 checkbox，**用回應的 `category_ids` 預先勾選**）＋每列儲存鈕 |

### 3.1 切換類別時已選地點的處理

切換類別 → **重載地點／說明清單**；若目前選中值不在新清單 → **清空＋提示「地點已重設，請重新選擇」**。

### 3.2 留言框過濾

`category_id` 存在但 inactive → **照常過濾回傳（200）**；只有 id 不存在或 type≠'category' → `400`。前端不需 fallback 邏輯。

### 3.3 類別停用時

**類別停用 → 僅該類別從建單下拉消失，`option_categories` 列保留不動**（重新啟用即恢復）。**禁止 `DELETE FROM option_categories`**。

### 3.4 P7 勾選矩陣儲存

**每列一個「儲存」鈕，按下才送完整勾選清單**（全量覆寫）。即時送出容易網路不穩時覆寫成半套。

> **手機可用性**：若類別數長到 10+，每列橫向 checkbox 難點。建議「點某一列 → modal 勾選」。目前 seed 7 類別，臨界值附近，施工時依實際類別數決定。
