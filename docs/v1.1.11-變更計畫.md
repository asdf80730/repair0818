## 第一部分 🔴 A — 會實際踩到的功能 bug（4 項）

### A1. `PATCH /api/tickets/:id` 改類別 → `NOT NULL constraint failed` 崩潰 500
- **位置**：`src/routes/tickets.ts` PATCH handler（改類別且原地點不相容時 `newLocationLabel = null`）
- **根因**：`tickets.location_label` 有 `NOT NULL`，寫入 null 觸發 SQLite 崩潰
- **改法**：改類別後若原地點不相容，**回 `400 VALIDATION_ERROR` 要求使用者重選地點**，而非寫 null。具體：`else if (body.category_id !== undefined && body.category_id !== ticket.category_id)` 分支內，`if (!locAllowed) return fail(c, 400, 'VALIDATION_ERROR', '此地點不屬於新類別，請重新選擇地點')`，並移除 `newLocationId = null; newLocationLabel = null` 與 `地點 ...→（清空）` 的 changes 寫法
- **優先級**：🔴 高（500 崩潰）
- **影響**：改類別且地點不相容的編輯操作，從崩潰改為明確提示
- **⚠️ 規格/測試同步（補充 1）**：既有測試**無**「只改類別→舊地點清空回 200」的斷言（`assoc.test.ts` 的「location 不屬於 category 且非通用 → 400」正是本項目要達成的既有行為，**不會紅燈**）；但 `SPEC.md §4.3` PATCH 的「改類別/地點時快照 label 同步更新」描述需補一句「改類別後若原地點不相容 → 回 400 要求重選」，維持文件與行為一致

### A2. `csrfGuard` 阻擋無 body 的 Mutation 請求（403）
- **位置**：`src/lib/csrf.ts` 第 3 步 content-type 檢查
- **根因**：無 body 的 POST（share-token、logout）`api()` 不設 Content-Type → `contentType=''` → 非 json 非 multipart → 403
- **改法**：僅在「**有 body 且非 json/multipart**」時 403。具體結合 `Content-Length` 判斷避免「有 body 但清空 Content-Type」繞過（補充 4）：
  ```typescript
  const contentType = c.req.header('Content-Type') ?? ''
  const contentLength = c.req.header('Content-Length')
  const hasBody = contentLength !== undefined && contentLength !== '0'
  const isMultipart = contentType.startsWith('multipart/form-data')
  if (hasBody && !isMultipart && !contentType.startsWith('application/json')) {
    return fail(c, 403, 'FORBIDDEN', '不支援的 Content-Type')
  }
  ```
  （純用 `if (contentType && ...)` 時，攻擊者帶 body 卻清空 Content-Type 可繞過；用 `hasBody` 判讀 Content-Length 較嚴謹）
- **優先級**：🔴 高（share-token、logout 目前 403 失效）
- **影響**：修復重新產生分享連結、登出功能；維持 CSRF 防線

### A3. CSV 匯出 from/to 時區偏差 8 小時
- **位置**：`src/routes/exports.ts` `buildCsv`（`from + 'T00:00:00.000Z'`）
- **根因**：規格 from/to 是台灣日期，DB 存 UTC；直接拼 Z 造成台灣 00:00–08:00 的單被漏掉
- **改法**：換算為台灣時區對應的 UTC。具體：`new Date(from + 'T00:00:00+08:00').toISOString()`（to 同理 `+08:00` 的 23:59:59）
- **優先級**：🔴 高（匯出資料缺漏）
- **影響**：CSV 篩選日期正確涵蓋台灣整天

### A4. `POST /api/options` 未防護 `comment_desc` 寫入關聯表
- **位置**：`src/lib/validate.ts` `createOptionSchema`＋`src/routes/options.ts`
- **根因**：SPEC/CLAUDE 明定 `comment_desc` 不參與類別關聯，但 zod 只擋 `type==='category'` 帶 category_ids，`comment_desc` 帶 category_ids 仍會寫入 option_categories
- **改法**：`superRefine` 對 `category` 與 `comment_desc` 都禁止帶 `category_ids`。具體：`if ((val.type === 'category' || val.type === 'comment_desc') && val.category_ids !== undefined) ctx.addIssue(...)`
- **優先級**：🔴 高（資料契約違反）
- **影響**：回報範本不再可能被誤綁類別

## 第二部分 🟡 B — 防禦性／效能（4 項）

### B1. CSV update_count 全表掃描 `ticket_updates`（忽略篩選）
- **位置**：`src/routes/exports.ts` `buildCsv`
- **根因**：目前二次全表掃描 `SELECT ticket_id, COUNT(*) ... GROUP BY ticket_id`，與主查詢篩選無關
- **改法**：改在主 SQL 用子查詢算 `update_count`，省二次全表掃描。具體：主 SELECT 加 `(SELECT COUNT(*) FROM ticket_updates u WHERE u.ticket_id = t.id AND u.kind = 'status') AS update_count`
- **優先級**：🟡 中（資料多才有感）

### B2. hash router 未過濾 query string
- **位置**：`public/app.js` router（`hash.slice(1).split('/')`）
- **影響**：`#/ticket/12?ref=share` 把 param 解析成 `12?ref=share` → 後端 Number 判 NaN → 400
- **改法**：解析 hash 前先 `split('?')[0]`。具體：`const hash = (location.hash || '#/').split('?')[0]`
- **優先級**：🟡 中（外部帶 query 的連結）

### B3. `toTaipeiDisplay` 遇 Invalid Date 丟未捕捉例外
- **位置**：`src/lib/time.ts`
- **改法**：`if (!iso) return ''`、`if (isNaN(d.getTime())) return ''`
- **優先級**：🟡 中（防禦）

### B4. D1 動態 IN 陣列無分塊（可能超綁定上限）
- **位置**：`src/routes/tickets.ts`（updatePhotos）、`src/routes/options.ts`（assoc）、`src/lib/db.ts`（validateOwnUnboundPhotos/assertCategoryIds）
- **影響**：工單歷史回報多時，`IN (?,?,...)` 超過 D1 綁定上限
- **改法**：大批量 IN 分塊（每 50 個一組），或改 JOIN 取照片
- **優先級**：🟡 中（資料多才有感）

## 第四部分 🔴 D — 業務功能缺失（9 項，P0）

### D1. 廠商指派後無法清空（與 G1 同批施工）

- **優先級**：🔴 高（功能缺失）
- **⚠️ 依賴**：**必須與 G1 同批施工**，否則清空失效

### D2. 編輯頁地點未依類別連動
- **位置**：`public/app.js` `pages.edit`
- **根因**：edit 頁 `locSelect` 載入全部地點、`catSelect` 無 change 監聽 → 選到不屬類別的地點送出會 400
- **改法**：edit 頁比照建單頁加 `filterByCat('locations')` 連動

- **位置**：`public/app.js` `silentRelogin`（`return body` 不檢查 `retry.ok`）

- **根因**：`options(UNIQUE type,label)` 約束，改撞名 label 直接 500，無捕捉
- **改法**：更新前查 `(type,label)` 是否被其他 id 占用，或 catch 轉 400「標籤已存在」
- **優先級**：🔴 高（500）

### D5. 表單無防重複點擊（double-submit）
- **位置**：`public/app.js` `pages.new`、`pages.ticket`
- **根因**：送出鈕無 disabled／無 `isSubmitting` 旗標 → 連點兩次重複建單或重複留言
- **改法**：送出時設 `isSubmitting`，成功／失敗後再清除
- **優先級**：🟡 中（重複資料）

### D6. 外部瀏覽器 CSV 匯出被 Safari 彈窗攔截
- **位置**：`public/app.js` `exportCsv`（`window.open` 在 `await` 後）
- **根因**：非同步後 `window.open` 失去使用者手勢信任 → iOS 阻擋
- **改法**：非 LIFF 環境改用 `window.location.href = url`
- **優先級**：🟡 中（iOS 匯出）

### D7. 成員角色變更失敗 UI 未回滾
- **位置**：`public/app.js` `pages.users` roleSelect catch
- **根因**：catch 只 `alert` 沒 `render()`，下拉停留在錯誤角色

### D8. 開通成員未記錄 `approved_at`

### D9. comments 寫入未用 batch（違反 CLAUDE 規則）

## 第五部分 🟡 E — 行動端 UX／並發／資源生命週期（10 項）

### E1. 照片上傳無 5 張上限檢核、無刪除按鈕
- **位置**：`public/app.js` 建單 `selectedPhotos`/`photoPreview`、留言框 `commentPhotos`/`commentFile`
- **根因**：前端只 push 不計數、預覽區單向 appendChild 無刪除鍵 → 分批選 >5 張必 400、選錯無法取消。**留言框 `commentPhotos` 連縮圖預覽都沒有**
- **改法**：`selectedPhotos.length >= 5`／`commentPhotos.length >= 5` 時擋下後續選取；預覽縮圖加 ✕ 刪除鍵（留言框補縮圖預覽）；已刪除者連同 id 移除
- **⚠️ 累積計數（補充 5）**：分多次選取時，`change` 事件須先算 `selectedPhotos.length + photoInput.files.length > 5`，**在上傳到 `/api/photos` 前**立即阻斷並提示，避免把照片傳到 R2 後才被後端拒絕（浪費頻寬＋產生孤兒照片）
- **優先級**：🟡 中（體驗）

### E2. LINE WebView 剪貼簿複製無 fallback／無反饋
- **位置**：`public/app.js` 複製分享連結

- **改法**：加 try/catch fallback 到 `document.execCommand('copy')`，成功後 toast「已複製」
- **優先級**：🟡 中（行動端）

### E3. 列表「載入更多」快速連點重複渲染
- **位置**：`public/app.js` `loadMore`
- **根因**：連點兩次同 page 發兩請求，appendChild 重複渲染同頁卡片

- **優先級**：🟡 中（重複資料）

### E4. iOS 底部 Home 條遮擋導覽列（缺 safe-area）

- **根因**：`#nav fixed bottom:0` 無 `env(safe-area-inset-bottom)` → iPhone X+ 被 Home 指示條遮
- **改法**：`#nav` 加 `padding-bottom: env(safe-area-inset-bottom)`
- **優先級**：🟡 中（行動端）

### E5. `POST /options/:id/assoc` 200 筆關聯超出 D1 batch 上限

### E6. `GET /exports/tickets.csv` 軌道 A 未掛 Zod 驗證
- **位置**：`src/app.ts`＋`src/routes/exports.ts` `csvDownload`

### E7. `assertValidAssoc` 空陣列跳過 type 檢查

### E8. 雙管理員互相降權的「零管理員」競態

### E9. R2 孤兒照片（DB 寫入失敗未清理 R2）

### E10. P7 改選項後全域快取未清

- **優先級**：🟡 中（快取一致性）

## 第六部分 🔴 F — 非同步競態／索引／UI／死碼（8 項）

### F1. P7 關聯 Modal 尚未載入完成時點「儲存」會清空該類別所有關聯
- **位置**：`public/app.js` `pages.admin` 的 `openAssocModal`
- **根因**：建立 Modal 後立即發出兩個非同步請求載入地點/說明選項，但「儲存」按鈕無 `disabled` 也無 loading 遮罩。若在載入完成前點儲存，`querySelectorAll('input:checked')` 為空 → 送 `POST /api/options/:id/assoc` 帶 `{ option_ids: [] }` → **該類別原本所有關聯被全量覆寫清空**（資料破壞）
- **改法**：選項載入完成前將儲存鈕 `disabled`，並在 Modal 內顯示載入指示器；載入完成後才啟用
- **優先級**：🔴 高（**資料破壞**）

### F2. P7 管理頁 Tab 快速切換引發渲染覆蓋（Stale Response Overwrite）
- **位置**：`public/app.js` `pages.admin` 的 `renderVendors`/`renderOptions`
- **根因**：切換 Tab 更新 `currentType` 後非同步呼叫 render，各 `.then((b) => { content.innerHTML = ... })` 直接覆蓋內容，無 `currentType` 比對。若「廠商」回應較慢抵達，會在「地點」載入後覆蓋 → **Tab 顯示「地點」但內容是「廠商」**
- **改法**：`.then()` 回呼內比對 `if (currentType !== thisType) return`（或記錄請求序號，只接受最新）
- **優先級**：🔴 高（UI 錯亂）

### F3. 平行 401 請求引發雷鳴群（Thundering Herd）與連鎖 Session 簽發
- **位置**：`public/app.js` `silentRelogin`
- **根因**：Session 過期時，含多個平行 API 呼叫的頁面（如 P1 同時請求 `/api/tickets` 與 `/api/options/catalog`）會各自收到 401 並各自進入 `silentRelogin`，同時向 `/api/auth/session` 發多次重複 POST、後端對 LINE 驗證伺服器發多次相同 ID Token 驗證，造成網路開銷與 Cookie 覆寫競態
- **改法**：建立全域 `reloginPromise` 單例，平行觸發的 401 共用同一次靜默重登流程
- **優先級**：🟡 中（並發）

### F4. 統計查詢缺少複合索引導致全表掃描
- **位置**：`migrations/0001_init.sql`（`idx_updates_ticket`）＋ `src/routes/stats.ts` month_done 查詢
- **根因**：`ticket_updates` 僅有 `idx_updates_ticket(ticket_id, created_at)`；month_done 需同時過濾 `kind`、`status`、`created_at`，無對應索引 → 每次瀏覽統計頁都全表掃描，隨歷史回報增多延遲線性上升
- **改法**：新增 migration 補 `CREATE INDEX idx_updates_stats ON ticket_updates(kind, status, created_at)`（**不可改 0001**，0001 已套 production，須用新 migration file）
- **⚠️ 檔名（補充 3）**：新檔必須命名為 **`migrations/0005_updates_stats_idx.sql`**（現有 0001–0004，下一個序號是 0005），避免檔名衝突導致 D1 migration 覆蓋或跳過
- **優先級**：🟡 中（效能）

### F5. 案件列表分頁缺少次要排序鍵（Tie-Breaker）導致分頁不穩定
- **位置**：`src/routes/tickets.ts` GET /api/tickets 的 `ORDER BY t.last_activity_at DESC LIMIT ? OFFSET ?`
- **根因**：多筆 `last_activity_at` 相同（seed 或批次匯入）時排序不確定，`LIMIT/OFFSET` 分頁可能跨頁重複或遺漏案件
- **改法**：加唯一鍵次要排序 `ORDER BY t.last_activity_at DESC, t.id DESC`
- **優先級**：🟡 中（分頁穩定性）

### F6. 建單頁選取「零關聯類別」引發無限重複 Alert 彈窗
- **位置**：`public/app.js` `pages.new` 的 `catSelect` change handler
- **根因**：`if (locs.length === 0 || descs.length === 0)` 就 `alert`＋`ensureCatalog(true)`。若類別真的無關聯（重抓後仍空），每次切換到該類別都重複彈窗＋重抓，無法消除
- **改法**：僅在「快取可能過期」時重抓一次；重抓後仍空則改為非阻斷提示（如下拉顯示「此類別尚無可用選項」），不再重複 alert
- **優先級**：🟡 中（體驗）

### F7. 案件詳情主照片與時間軸照片的 Lightbox 行為不一致
- **位置**：`public/app.js` `pages.ticket` 主照片牆（`el('img', { class: 'photo' })`）vs 時間軸照片（`thumb()`）
- **根因**：時間軸照片用 `thumb()` 內建 `openLightbox`；主照片牆直接建原生 `<img>` 無 onclick → 點主照片無反應，破壞一致性
- **改法**：主照片牆改用 `thumb()`（或綁 `openLightbox`）
- **優先級**：🟡 中（UI 一致性）

### F8. `src/routes/tickets.ts` 殘留未使用的宣告變數（死碼）
- **位置**：`src/routes/tickets.ts` PATCH handler 的 `const labelMap: Record<string, string> = {}`（第 257 行）
- **根因**：先前版本用於欄位變更對照的殘留，現已改由 `changes.push(...)` 組裝，`labelMap` 宣告後完全未讀未寫
- **改法**：移除 `labelMap` 宣告
- **優先級**：低（死碼）

## 第七部分 🟡 G — 邏輯運算子／資料契約／留痕（8 項）

### G1. `newVendorId ?? ticket.vendor_id` Nullish 陷阱導致 null 清空失效
- **位置**：`src/routes/tickets.ts` PATCH handler 的 UPDATE 綁定 `newVendorId ?? ticket.vendor_id`（第 317 行）
- **根因**：`??` 將 `null` 與 `undefined` 一併視為空值回退。**一旦照 D1 開放 `vendor_id` 可設 `null` 清空，傳入 `newVendorId = null` 時會回退寫回原 `ticket.vendor_id`，永遠無法把已指派的廠商重設為空**
- **改法**：**與 D1 同批施工**——不可用 `??`，改用三態判斷：`newVendorId === undefined ? ticket.vendor_id : newVendorId`（undefined=不變、null=清空、有值=指派）
- **優先級**：🔴 高（**D1 施工前提**）

### G2. 類別停用導致關聯選項「永久幽靈孤兒化」
- **位置**：`src/routes/options.ts` `/catalog` 端點（讀全部 `option_categories` 不過濾 active）＋ `src/lib/db.ts` `optionAllowedInCategory`
- **根因**：catalog 讀所有關聯列未過濾 `options.active=1 AND type='category'`。停用類別後其關聯列仍保留（CLAUDE 規則），該類別關聯到的地點/說明 `category_ids.length>0` 不會被判通用，但停用類別在下拉又不可選 → **該地點/說明在全系統所有類別下徹底隱形、無法被選取**（與 CLAUDE「停用類別不 DELETE 關聯」規則衝突）
- **改法**：`/catalog` 的關聯查詢 JOIN options 過濾 `o.active = 1 AND o.type = 'category'`（僅保留有效類別關聯）；`optionAllowedInCategory` 同步確認
- **⚠️ 業務語意邊界（補充 2）**：**不可**直接將停用類別的關聯剔除後讓其專屬地點/說明變成「通用（所有類別可見）」——那會讓原本專屬「電梯（已停用）」的地點（如「電梯機房」）突然曝光在「照明」「水泵」等其他類別下拉。建議：
  - **建單下拉（catalog）**：維持現況（專屬已停用類別的選項不應在其他類別出現）
  - **管理頁（P7）**：僅在 P7 類別管理與 Modal 勾選時過濾掉已停用類別的關聯項，或在停用類別時提示管理員「該類別下尚有專屬地點/說明，是否轉為通用或移轉關聯」
- **優先級**：🔴 高（**資料隱形**）

### G3. 常用範本附加的 `includes()` 子字串誤判
- **位置**：`public/app.js` 建單 `pages.new` 與留言框 `pages.ticket`（`if (cur.includes(label)) return`）
- **根因**：以子字串比對防重複附加，若說明欄已含「中庭**其他**設施」而範本標籤為「其他」，`cur.includes('其他')` 為 true → 簡短標籤（其他/漏水/門禁）撞名自訂文字時**無法附加**
- **改法**：改以「附加片段為獨立項目」判斷（如比對 `cur` 以「、」切分後的陣列是否已含該 label），而非裸 `includes`
- **優先級**：🟡 中（體驗）

### G4. 列表 API 遺漏停用廠商標註，與詳情 API 不一致
- **位置**：`src/routes/tickets.ts` GET /api/tickets（列表）vs GET /api/tickets/:id（詳情）
- **根因**：詳情端廠商停用時後綴「（已停用）」；列表端只 `LEFT JOIN vendors v` 輸出 `v.name`，未讀 `v.active` → **同一案件列表顯示正常名、點入詳情才顯示「（已停用）」**，資料契約不一致
- **改法**：列表查詢加 `v.active`，同詳情端後綴「（已停用）」
- **優先級**：🟡 中（資料契約）

### G5. 系統變更留痕遺漏廠商名稱追蹤
- **位置**：`src/routes/tickets.ts` PATCH `changes.push('廠商')`
- **根因**：類別/地點留 before→after（`類別 電梯→門禁`），但指派廠商只寫「廠商」，時間軸無從得知由哪家轉派給哪家，喪失派工歷程追溯
- **改法**：`changes.push(\`廠商 ${oldName}→${newName}\`)`（取舊 vendor name 與新 vendor name）
- **⚠️ 主查詢需補 JOIN（補充 1）**：PATCH 主查詢目前是 `SELECT id, category_id, ..., vendor_id FROM tickets WHERE id = ?`，**未含 `vendor_name`**。要記錄 `廠商 舊→新`，主查詢必須加 `LEFT JOIN vendors v ON v.id = t.vendor_id` 同步查出 `v.name AS vendor_name`，否則比對/寫入時間軸時拿不到舊廠商名會出現 `undefined`
- **優先級**：🟡 中（留痕）

### G6. Reopen 備註為空時殘留格式符號
- **位置**：`src/routes/tickets.ts` POST /:id/reopen 的 `重新開啟（原狀態：${prevStatusLabel}）：${body.note ?? ''}`
- **根因**：備註未填時時間軸記錄帶尾端冒號的空字串「重新開啟（原狀態：已完成）：」，版面殘留未完成標點
- **改法**：`body.note ? \`：${body.note}\` : ''`（無備註時不帶冒號）
- **優先級**：🟡 中（版面）

### G7. 公開派工照片端點缺 `Content-Disposition: inline`
- **位置**：`src/routes/share.ts` GET /:token/photos/:photo_id
- **根因**：內部照片端點（photos.ts）有 `Content-Disposition: inline; filename=...`，公開端點僅 Content-Type + Cache-Control → 部分 Android 內建瀏覽器/通訊軟體可能觸發下載對話框而非頁內渲染
- **改法**：share 照片端點補 `Content-Disposition: inline; filename="photo-{id}.jpg"`（副檔名依 content_type 推斷）
- **優先級**：🟡 中（相容）

### G8. zod `optionalText` 拒絕 null 欄位（低風險）
- **位置**：`src/lib/validate.ts` `optionalText = z.string().trim().max(max).optional().or(z.literal(''))`
- **根因**：`{ description: null }` 非 `undefined` 非 `string` → 400。僅外部 HTTP 客戶端/自動化工具送標準 REST `null` 才觸發（SPA 前端送 `undefined` 不影響）
- **改法**：`z.string().trim().max(max).optional().nullable()` 或 `z.preprocess` 將 null 轉 undefined；低風險、可彈性取捨
- **優先級**：低（相容）

## 第八部分 🟡 H — 資料純淨化／公開派工頁／維運（5 項）

> 第七份補充 review 的 5 個新盲點，全部讀碼驗證屬實。

### H1. `tickets.description` 清空時由 `""` 轉 `NULL`（資料純淨化）
- **位置**：`src/routes/tickets.ts` PATCH handler（`newDescription = body.description`）
- **根因**：建單時未填說明存 `NULL`（`body.description ?? null`，但空字串 `""` 會存成 `""`）；編輯時刪除既有說明變 `""` → `newDescription` 被寫成 `""`，與 `NULL` 欄位狀態不一致
- **改法**：寫入前正規化：`newDescription = body.description.trim() === '' ? null : body.description`；建單端 `body.description ?? null` 也建議改 `body.description?.trim() || null`
- **優先級**：🟡 中（資料一致性）

### H2. 公開派工頁（`share.html`）遺漏照片 Lightbox
- **位置**：`public/share.js`（照片牆 `el('img', { class: 'photo' })` 無 onclick）
- **根因**：F7 修了內部詳情頁主照片 Lightbox，但 `share.js` 是獨立腳本，**完全沒補**。外部廠商開派工連結點照片無反應，無法放大看損壞細節/銘牌
- **改法**：在 `share.js` 補獨立 `openLightbox(src)`（同 app.js 的 lightbox，用 mask + img），為照片綁定點擊放大
- **優先級**：🟡 中（外部廠商 UX）

### H3. `GET /api/share/:token/photos/:photo_id` 缺 `:photo_id` 整數防禦
- **位置**：`src/routes/share.ts`（`const photoId = Number(c.req.param('photo_id'))`）
- **根因**：有 token UUID 格式檢驗，但 `photo_id` 傳非數字（`/photos/abc`）→ `Number('abc')=NaN`。SQLite 比對 `p.id = NaN` 雖不報錯回 null，但缺顯式型別檢核
- **改法**：`if (!Number.isInteger(photoId) || photoId <= 0) return fail(c, 404, 'NOT_FOUND', '照片不存在')`
- **優先級**：🟡 中（防禦）

### H4. Migration 套用指令須用正確 DB 名稱 `repair-db0818`
- **位置**：`README.md`/`docs/SPEC.md §8.3` 指令範例 vs `wrangler.toml`（`database_name = "repair-db0818"`）
- **根因**：`SPEC.md` 的 migration 範例寫 `repair-db`，實際 DB 是 `repair-db0818`。執行 F4（0005）套 production 若複製舊名稱會回 `Database not found`
- **改法**：套用確認用 **`npx wrangler d1 migrations apply repair-db0818 --remote`**；同步修正 SPEC §8.3 指令
- **優先級**：🟡 中（維運）

### H5. 圖片缺 `cursor: pointer` 手勢指引
- **位置**：`public/style.css`（`.thumb`/`.photo` 無 cursor）
- **根因**：可放大照片在桌面/iPad 滑鼠懸停時無手指游標，降低可點擊性暗示
- **改法**：`public/style.css` 補 `.thumb, .photo { cursor: pointer; }`
- **優先級**：低（微互動）
