## Findings

### 1. 文件版本一致性缺确定性檢查（automated check，本輪最重）

審查抓到四處同因漂移：SPEC 檔頭 `v1.1.32` vs §0.1 首列 `v1.1.33`、`e2e/message-templates.spec.js:4` 與 `tests/stats.test.ts:789` 滯留 v1.1.32、SPEC 內「migration 0013」引用（squash 後實檔只到 0003）。這是機械性錯誤，值得一支 deterministic script 而非新規則：

- 檔頭 `**版本：v1.1.NN**` 須等於 §0.1 表格首列 `| v1.1.NN |`——可字串比對，零誤判。
- 「檔頭引用不存在的 `migrations/NNNN_*.sql`」——比對 `docs/**/*.md` 的 `migration 0\d{3}` 與實檔清單，drift 即紅。
- 掛法：`scripts/check-doc-versions.py`，進 CI（test job 最後一步）；pre-commit 太敏感（改 SPEC 例就擋），先只進 CI。

殘餘殘留型漂移（測試／e2e 檔內版號註解）難機械化判「該不該更新」——留給審查規則（見 #2 的出鏈清單 #3）。

### 2. 時間敏感斷言的出鏈教訓（coding standard／出鏈清單）

昨日 retro 才記「標題斷言帶天數保唯一」，今日 `hardcode (53 天)` 照樣進 main——若有人跨過 10-10 沒收口，CI 隔天即紅（今天 10-11 未紅只因先修了）。教訓：「帶天數」不夠，要**帶到不會隨時間變的值格式**＝`/\(\d+ 天\)/` regex＋`.first()`（mock 有同標題雙列 53/0 天，strict mode 需斷）。寫進 e2e 慣例；審查者看到 `getByText(".*\(\d+ 天\)")` 字串硬編＝改 regex。

### 3. 版本定版出鏈清單（navigation）

本版漂移全在「改程式沒帶到的註解／檔頭」；同「去編號出鏈清單」（retro 10-10 #3）性質。定版動 SPEC 時同步點：

1. `docs/SPEC.md:3` 檔頭＋日期
2. `docs/SPEC.md` §0.1 新列
3. 程式碼內該版行為註解（例：`stats.ts` daily-report 標頭）
4. `tests/`、`e2e/` 檔頭與斷言旁註解的版號
5. SPEC 內引用的 migration 編號（改 squash 狀態時）

### 4. 佈局改動的「內聯 probe」驗證路徑（information access）

本輪實測：CSS 改動對 production 打 e2e 驗不到（线上是舊 CSS）、本機 dev server 又不可靠（CLAUDE.md 已記 wrangler×Bun 崩潰）→ 驗證改佈局的正解＝**內聯 probe**：`playwright` 直接 `chromium.launch()` ＋ `page.setContent(html)`（html 內聯真實 CSS 變數＋真實 pill 文案）＋ 390/360 viewport 測 `rows`（top 去重）／`docW==vw`／`scrollWidth`。30 秒得實測值，免部署免起 server。記為佈局變更標準驗證手路；`page.evaluate` 回傳必須 `JSON.stringify` 現值（Bun 沒 `JSON.stringfy` 這種 typo 會直接崩，屬正常報錯）。
