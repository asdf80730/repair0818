## 施工避坑指南（第十二輪補充）

> 針對 A 類核心項目的實作陷阱，施工時務必遵守。

### A1 詳情合併查詢 — json_group_array 空值陷阱
- `LEFT JOIN photos` + `json_group_array` 在**無照片**時會產出 `[{"id":null}]` 而非 `[]`。
- 用 `CASE WHEN COUNT(p.id)=0 THEN json('[]') ELSE json_group_array(...) END` 防坑。

### A4 統計頁月份切換 — 雙 API 同步
- P5 有兩區塊：`/api/stats/summary?month=` 與 `/api/stats/amount-by-category?month=`。
- 切月份時用 `Promise.all([summary, amountByCategory])` 同步刷新，避免上下月份不一致。
- **現況**：目前分開抓（summary `.then`、amount `await`），需改 Promise.all。

### A5 逾期 Tab — 排除已結案/作廢
- 篩選 `>7天` 務必排除 `done`/`void`。
- **現況**：卡片 stale 已排除（`status==='open'||'in_progress'`），新增 Tab 沿用此條件。

### A3 完成率語意（2026-08-22 決策：方案②）
- 完成率＝「本月結案 / (期初未結案 + 本月新增)」。
- **「期初未結案」定義**：本月月初時點**尚未結案**的案件數（＝ open + in_progress；done/void 不計）。因 `tickets.status` 是「目前狀態」快照、reopen 會改狀態，無法直接用現存 status 回溯月初——須以「月初時點」推導：**現在仍非 done/void 的案件**（不管何時建）＋**月初後才結案、但月初時仍開著**的案件（用 `closed_at` 與月初邊界比對）。
- 分母避免為 0：`期初未結案 + 本月新增` 為 0 時完成率顯示 `—`，不除零。
- 前端 `pages.stats` 的 `doneRate` 目前 `month_done/month_new`，改以新分母計算。
- 需同步 SPEC §4.7 完成率語意，並與 `month_done`（append-only `ticket_updates` 不重複案件）一致，避免 reopen 回溯改變。

### A6 session 滑動續期 — Cookie 屬性一致
- 換發 JWT 的 `Set-Cookie` 屬性須與登入一致：`Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600`。
- 注意 Hono middleware 順序，避免換發的 Set-Cookie 被後續 handler 覆寫。

### A7 CI 版本比對 — CF_PAGES_COMMIT_SHA
- Cloudflare Pages 建置自動注入 `CF_PAGES_COMMIT_SHA`。
- `/api/hello` 回傳 `{ ok, commit: env.CF_PAGES_COMMIT_SHA || 'dev' }`，CI 比對 `res.commit === github.sha`。
- **現況**：hello 未回傳 commit，需改。

### E3 — void/reopen 避免寫入錯誤時間軸（先 UPDATE 成功才 INSERT）

**問題**：原兩端點 `batch([UPDATE tickets(帶狀態條件), INSERT ticket_updates(無條件)])` 原子提交，UPDATE 影響 0 筆時 INSERT 仍成功 → 並發時回 400 卻留假紀錄。

**實作（v1.1.14）改為兩步寫入**：先 `UPDATE ... .run()`，以 `meta.changes` 判斷；成功才寫時間軸 INSERT。

> ⚠ 曾嘗試 `INSERT...SELECT...WHERE EXISTS` 放同一 batch，但 **batch 內依序執行**——第一個 UPDATE 先改狀態，第二個 INSERT 的 EXISTS 已讀到「新狀態」，反而永遠 0 筆 → 400。故不能靠 batch 內 EXISTS，須兩步。

**src/routes/tickets.ts — POST /:id/void**：

```diff
   const now = nowIso()
-  // #1：樂觀鎖——UPDATE 帶狀態條件，防止雙 admin 同時作廢造成重複寫入
-  const batchRes = await c.env.DB.batch([
-    c.env.DB.prepare(
-      "UPDATE tickets SET status = ?, closed_at = ?, closed_by = ?, last_activity_at = ? WHERE id = ? AND status IN ('open','in_progress')",
-    ).bind('void', now, user.id, now, id),
-    c.env.DB.prepare(
-      `INSERT INTO ticket_updates (ticket_id, user_id, kind, status, note, created_at)
-       VALUES (?, ?, 'status', 'void', ?, ?)`,
-    ).bind(id, user.id, body.note ?? null, now),
-  ])
-  if (batchRes[0].meta.changes === 0) {
-    return fail(c, 400, 'VALIDATION_ERROR', '案件狀態已變更，請重新整理')
-  }
+  // 樂觀鎖：UPDATE 帶狀態條件，防止雙 admin 同時作廢
+  const upd = await c.env.DB.prepare(
+    "UPDATE tickets SET status = ?, closed_at = ?, closed_by = ?, last_activity_at = ? WHERE id = ? AND status IN ('open','in_progress')",
+  ).bind('void', now, user.id, now, id).run()
+  if (upd.meta.changes === 0) {
+    return fail(c, 400, 'VALIDATION_ERROR', '案件狀態已變更，請重新整理')
+  }
+  // 狀態確已變更，寫入時間軸
+  await c.env.DB.prepare(
+    `INSERT INTO ticket_updates (ticket_id, user_id, kind, status, note, created_at)
+     VALUES (?, ?, 'status', 'void', ?, ?)`,
+  ).bind(id, user.id, body.note ?? null, now).run()
```

**POST /:id/reopen 同理**：`UPDATE ... WHERE id = ? AND status IN ('done','void')`，以 `meta.changes === 0` 判斷回 400，成功才 INSERT 時間軸。

**注意**：
- 兩步非原子（無 D1 互動式交易），但 UPDATE 成功後 INSERT 失敗極罕見；INSERT 只是留痕，若失敗可用後端錯誤對應。
- 補測試：`tests/ticket-actions.test.ts`「雙 void」「雙 reopen」— 第二個應回 400 且**不產生第二筆時間軸**。

### F3 — 狀態流後端驗證（2026-08-22 已決策）

**決策**：鎖死退回（`in_progress→open` 禁）、允許 `open→done` 直接結案；`open→open` 禁。**`in_progress→in_progress` 允許**（多次發包覆寫 amount，v1.1.13 語意鎖死，勿禁）。合法轉移表：

```text
open        → in_progress | done
in_progress → in_progress | done
done        →（僅 reopen） ／ void 由 void 端點處理
void        →（僅 reopen）
```

**src/routes/tickets.ts — POST /:id/updates**，現行前置檢查：

```ts
  const ticket = await c.env.DB.prepare(
    'SELECT id, status FROM tickets WHERE id = ?',
  ).bind(id).first<{ id: number; status: string }>()
  if (!ticket) return fail(c, 404, 'NOT_FOUND', '案件不存在')

  // 已結案（done）或作廢（void）不可回報（§4.3）
  if (ticket.status === 'done' || ticket.status === 'void') {
    return fail(c, 400, 'VALIDATION_ERROR', '已結案或已作廢的案件不可回報')
  }
```

**改成（在 status 檢查後加轉移表驗證）**：

```diff
  if (ticket.status === 'done' || ticket.status === 'void') {
    return fail(c, 400, 'VALIDATION_ERROR', '已結案或已作廢的案件不可回報')
  }

+  // F3（v1.1.14 決策）：狀態流限制，鎖死退回、允許 open→done；in_progress→in_progress 允許（多次發包覆寫）
+  const ALLOWED_TRANSITIONS: Record<string, string[]> = {
+    open: ['in_progress', 'done'],
+    in_progress: ['in_progress', 'done'],
+  }
+  if (!(ALLOWED_TRANSITIONS[ticket.status] || []).includes(body.status)) {
+    return fail(c, 400, 'VALIDATION_ERROR', `狀態不可從 ${ticket.status} 轉為 ${body.status}`)
+  }
```

**注意**：
- `body.status` 經 `createUpdateSchema` 已是 `open/in_progress/done` 之一，轉移表只需處理三者。
- **reopen 不在此處驗**——`POST /:id/reopen` 已有自己的 done/void 限定，reopen 回 `in_progress/open` 屬另一條流程，不受此表約束（避免 reopen 回 open 被卡）。
- 前端 `comment-box` 的 `statusSelect` 目前列出 open/in_progress/done 全部選項，鎖死後 manager 在 `open` 案件選「已完成」會被後端擋 → **前端下拉須依 `t.status` 過濾選項**。
- 需補測試：`open→done` 允許、`in_progress→open` 拒絕、`open→open` 拒絕、`in_progress→in_progress` 拒絕（現 `tests/ticket-actions.test.ts` 只測「結案後不可回報」）。

**前端 public/app.js — comment-box 的 statusSelect 依案件狀態過濾**：

```js

//   open        → [in_progress, done]
```
